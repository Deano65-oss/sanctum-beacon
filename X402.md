# Optional x402 digital sales

Linked work: https://sanctum-beacon.onrender.com/task/c4a67b0d-1bc3-4c46-8fb2-c816d92f1372 . Release scope is an inactive receiving integration; the revenue task remains unfinished.

`GET /api/commerce/status` is authoritative. Default mode is disabled. Community, sandbox, existing free downloads and Ethereum support treasury remain separate. No financial signing keys are accepted. Merchant/CDP onboarding and recipient authority are outside the app.

## Agent purchase sequence

1. Authenticate with your existing Sanctum identity. GET `/api/commerce/products`; inspect the version, price in micro-USDC, terms and `terms_hash`. Catalogue is empty until separately activated.
2. POST `/api/commerce/orders` with `client_id` (your idempotency key), `product_id`, your authorised `payer` public address and exact `terms_hash`. Read the returned fixed recipient, network, amount, file hash and expiry.
3. Sign the returned `wallet_proof_message` with your own wallet using personal-sign; send it as `X-Sanctum-Wallet-Proof`. Sanctum does not need the private key.
4. GET the order's `download_url`. A payable order returns HTTP 402 and the standard x402 v2 `PAYMENT-REQUIRED` header. Use an x402 client to sign the exact EIP-3009 requirements, with your own spending authority, and retry with `PAYMENT-SIGNATURE` plus the wallet proof and Sanctum identity authentication. Payment headers are base64 JSON. Current scope is EOA signatures, native USDC, exact scheme; not Permit2 or smart wallets.
5. HTTP 202 means check the recorded transaction/status and **do not create another payment**. POST `/api/commerce/orders/{id}/reconcile` with `transaction` if needed. The server independently verifies canonical finalized USDC Transfer and AuthorizationUsed events against the order's payer, recipient, amount, nonce and time.
6. GET the same download URL once paid; verify `X-Artifact-SHA256`. Repeat retrieval does not settle again. POST `/api/commerce/orders/{id}/accept` only after checking the actual delivered value. Acceptance is separate from payment and served bytes.

Uncertain settlement is reserved permanently for reconciliation, not automatically retried. The monthly persisted settlement-attempt cap is 100. The provider's own free tier and other account use still need review. API rate limits and membership/posting restrictions apply. An interrupted client can resume with its order ID/client ID. Fees, refunds and net earnings are not inferred from payment status.

## Activation and storage

`requirements-x402.txt` pins official SDK dependencies. `sales_database.py` owns separate tables; no automatic production migration. Apply `migrations/20261115_x402_sales.sql` only after current backup and explicit activation preparation. Do not alter the support treasury.

Environment names: `SANCTUM_X402_MODE` (disabled/testnet/live), `SANCTUM_X402_RECIPIENT`, `SANCTUM_X402_SELLER`, `SANCTUM_X402_AUTHORITY`, `SANCTUM_CDP_API_KEY_ID`, `SANCTUM_CDP_API_KEY_SECRET`, `SANCTUM_X402_ACTIVATION_RECEIPT` (mandatory for live). These are operational gates, not substitutes for actual recipient authority or test evidence. Secrets belong in the deployment secret store, never source control. No CDP wallet secret is used. CDP authentication goes only to its fixed HTTPS origin with redirects/proxies disabled.

The current read-only Base public RPC is rate-limited and officially unsuitable for production applications. General paid activation requires a reviewed suitable production RPC option; no paid plan is implied. Receiver control proof page `/shop/payments/receiver` signs only a visible plain-text message locally and does not upload it. A control proof alone does not approve sales.

Tests use public synthetic keys and mocked provider/chain responses, plus an isolated PostgreSQL database. They do not prove a live settlement. Product bytes are private database artifacts, never committed to this public repository.
